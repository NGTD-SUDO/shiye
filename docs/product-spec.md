## 一、项目概述

**一句话定位**：把散落的纸质手写学科笔记拍下来，自动识别成文字、按学科归档，以后想找某个知识点，一搜就到。

**产品形态**（已确认）：
- 手机端（Android/iOS）：随手拍照/从相册导入 → 裁剪增强 → 归档到学科 → 搜索
- 电脑端（Windows）：批量导入、批量校对 OCR 文本、整理管理、导出备份

**核心卖点**（已确认）：手写文字识别 + 全文搜索。拍照后能按学科/关键词搜到笔记内容，**接受识别不完美**（人工校对闭环兜底）。

**暂定名**：候选「拾页 / 墨集 / 笔记匣」，已定名「拾页」。

---

## 二、用户与使用场景

**目标用户**：以学生（初高中/大学生）为主，本人整理自己的手写学科笔记，单用户为主、最多家人几台设备。

**三个核心场景**：
1. **随手收**（手机）：下课/复习后，把今天写的几页笔记拍照 → 选学科 → 归档。要求 30 秒内完成一页，流程短、可批量连拍。
2. **找得到**（手机/电脑）：考前复习，想找「导数求极值」的笔记 → 搜索框输入 → 命中页码列表 → 点开看原图。
3. **批量整**（电脑）：每周一次，把手机同步过来的笔记批量核对 OCR 文本、改名、移动学科、导出备份。

**非目标**（明确不做，防止跑偏）：
- 不做「在 App 里手写笔记」（对手是 GoodNotes，我们整理的是**纸质**笔记）
- 不做复杂协同/多人在线编辑
- 不做笔记社交/分享社区
- 不做复杂文档格式（Word/PDF 导出可以，导入不做）

## 三、竞品与差异点

| 产品 | 强项 | 为什么不是它 |
|---|---|---|
| GoodNotes / Notability | iPad 上手写体验顶级 | 在 App 里写，不是整理已有的纸质笔记；无中文手写全文搜索优势 |
| 扫描全能王 / 印象笔记扫描 | 扫描 + OCR 强 | 通用文档工具，无「学科→章→页」的学习整理结构，搜索是工具式不是复习导向 |
| MarginNote | PDF 批注 + 脑图 | 面向电子教材，非纸质手写笔记 |
| **本 App** | **为「纸质手写学科笔记」而生**：拍→识别→按学科归档→按知识点搜索→复习翻阅 | —— |

**差异本质**：竞品做「扫描仪」，我们做「学科笔记库」。

## 四、需求范围

### 4.1 功能清单

#### MVP（第一版必须可用）
**手机端**
1. 账号登录（手机号/邮箱 + JWT，沿用已验证的 FastAPI 后端模式）
2. 学科管理：增删改/排序/自定义颜色图标（用户自管理，长按编辑——长按编辑，减少层级）
3. 拍照归档：拍照/相册多选 → 手动裁剪（4 角拖动 + 增强滤镜）→ 选学科（可新建）→ 保存，支持连拍快速归档
4. 浏览：学科 → 章/页 两级浏览，网格 + 列表切换，图片缩放查看
5. 全文搜索：关键词搜索全部笔记，可按学科过滤；命中显示页码缩略图 + OCR 文本片段
6. OCR 状态可见：每页显示 识别中/完成/失败，可重试

**电脑端（Windows）**
7. 同一账号登录，浏览/搜索能力与手机一致
8. 批量导入：多选图片 → 选学科 → 批量入库并触发 OCR
9. 批量校对：左右分栏（左原图右 OCR 文本），逐页修正识别错误 → 修正结果同步进搜索索引
10. 批量操作：多选移动学科/删除

**后端（云服务器或本机自托管）**
11. REST API + SQLite + JWT（沿用已验证的成熟栈）
12. OCR 异步任务队列：上传即排队，完成后状态可查
13. 图片存储：服务器磁盘（MVP）→ OSS（量大后）

#### v2（MVP 验收后，按优先级排）
**AI 学情分析（用户确认的必要功能，紧随 M1 开发）**
- 一键生成学情报告：按学科统计页数 / OCR 识别完成率 / 笔记量趋势 → AI 输出薄弱点提示 + 复习建议
- 服务端 DeepSeek 单次轻请求（只发统计数字 + 学科/页标题文本，不发图片、不发全文），单次成本 <1 分
- 入口克制：学科详情页顶部按钮 + 「我的」页入口，不占 tab、不打断记录流程
- 数据太少 → 真实空态引导先记录，不硬出报告

- 自动裁剪（文档边缘检测，替换手动 4 角）
- OCR 结果定位高亮（识别词带坐标，点搜索结果词 → 原图上框出位置）
- 标题自动生成（取 OCR 首行）
- 导出备份 ZIP（整库图片+文本，可恢复）
- 手机端离线队列（无网先本地存，有网自动传）
- 深色模式

#### v3（远期，按需）
- 复习模式（按学科随机翻页/遮字回忆）
- 模糊搜索容错（错别字/拼音容错，jieba 分词）
- 多用户家庭共享（暂不需要则砍）
- 打印/PDF 导出精选页

### 4.2 明确不做的（此阶段）
- 手写笔记的批注编辑（圈画荧光笔）
- iOS 端发布（MVP 先 Android，架构上 Flutter 天然支持，后续补包即可）
- 多端实时协同编辑

## 五、总体架构

### 5.1 架构图

```
┌─────────────────────┐        ┌──────────────────────────────┐
│  手机端 (Flutter)     │  HTTPS │   云服务器（自托管服务器）    │
│  Android/iOS         │◄──────►│  FastAPI 后端                  │
│  拍照/裁剪/归档/搜索    │        │  ├─ REST API (JWT)             │
└─────────────────────┘        │  ├─ OCR 任务队列 (异步)          │
                               │  ├─ SQLite (元数据+OCR文本+索引)  │
┌─────────────────────┐        │  ├─ 图片存储 (磁盘→OSS)           │
│  电脑端 (Flutter     │        │  └─ OCR 引擎 (RapidOCR 自部署)    │
│   Windows 桌面)      │◄──────►│      │ 抽象层，可换百度手写API    │
│  批量导入/校对/管理    │        └──────────────────────────────┘
└─────────────────────┘
```

**数据流（核心闭环）**：
拍照/选图 → 客户端裁剪+压缩 → 上传(选学科) → 服务器存图、建记录、**投递 OCR 任务** → OCR 引擎识别 → 文本写回记录 → 客户端轮询到「完成」→ 文本进搜索索引 → 用户搜索命中 → 点开看原图 / 校对修正文本（修正也回写索引）

### 5.2 技术选型（全部沿用用户已验证的栈，不引入新玩具）

| 层 | 选型 | 理由 |
|---|---|---|
| 手机端 | Flutter（3.24+ 即可） | 一套代码出 Android/iOS |
| 电脑端 | Flutter Windows 桌面（同一仓库，多 target） | 与手机共享全部业务/UI 代码；批量管理逻辑复用 |
| 后端 | FastAPI + SQLAlchemy + SQLite + JWT | 个人数据量用 SQLite 绰绰有余，零运维 |
| OCR | 服务器端自部署 **RapidOCR**（PaddleOCR 模型 ONNX 版，CPU 可跑），**接口抽象可切换百度手写识别 API** | 免费、数据不出自己服务器（笔记隐私）；具体见第六章 |
| 搜索 | SQLite **FTS5 + trigram 分词** | 中文子串匹配友好；个人几千页毫秒级；无额外组件 |
| 图片处理 | 手机端 `image` 包（裁剪/压缩）；服务器 Pillow/OpenCV（OCR 前增强） | 轻量够用 |
| AI 赋能 | 云 API **DeepSeek**（单次轻请求，按次计费），预留自托管 Qwen 切换 | 中文强、便宜、零运维；记录类 App 的 AI 只需单次轻请求，不需要自建模型服务/向量库 |
| 部署 | 自托管（个人/家庭量级 1核2G 起）；图片走磁盘目录 | 摊薄服务器成本 |

### 5.3 关键架构决策
1. **OCR 放服务端不放手机端**：中文手写没有可用的端侧离线模型（ML Kit 不支持中文手写；手机跑 PaddleOCR 太重）。上传识别也顺带解决图片统一存储。
2. **识别文本可人工修正，且修正写回索引**：这是「接受识别不完美」的落点——识别错的字，校对一次，从此搜索就准。此闭环是产品可信度的根基，**MVP 必做**（电脑端批量校对页）。
3. **国内安卓无 GMS**：不用 Google ML Kit 文档扫描，裁剪先做手动 4 角框选（实现简单可靠），v2 再考虑自研边缘检测。
4. **数据归属用户**：自部署 OCR = 笔记图片不出自己的服务器；导出备份功能保证用户随时带走数据。
5. **AI 赋能克制原则（用户明确：AI 必要，但功能不要繁琐）**：只做「一次请求出一个结果」的轻功能（学情分析、章节总结），不做多轮对话、不建向量库 RAG、不做订阅体系；AI 只发必要文本（统计+标题）；结果直接可用，用户 3 步内看到结果。

## 六、OCR 方案（本产品最大技术风险，专章说清）

### 6.1 现实预期（管理期望，重要）
- 中文手写识别现状：**工整手写（一笔一画、行距清晰）单字/整行识别率可观（主观 80-90%）；连笔草书、涂改多、拍照歪斜模糊的页面，识别率会明显下降**。
- 印刷体（打印讲义/课本拍照）识别率接近 100%（RapidOCR 强项）。
- 用户已确认「接受识别不完美」→ 靠 6.3 校对闭环保证长期可用。

### 6.2 引擎选型对比与推荐

| 方案 | 成本 | 手写识别质量 | 隐私 | 运维 |
|---|---|---|---|---|
| **RapidOCR 自部署**（推荐默认） | 0（开源） | 中上（PP-OCR 模型对手写有基础泛化，印刷体极强） | ✅ 数据不出服务器 | 装一次，CPU 推理单页约 1~3s，异步队列可接受 |
| 百度云「手写文字识别」API | 约 ¥0.01~0.02/次，有免费额度 | 高（专门手写模型） | 图片上传百度 | 零运维，按量付费 |
| 腾讯/阿里云 OCR | 同上量级 | 高 | 同上 | 同上 |

**决策**：
1. 后端定义 `OcrProvider` 抽象接口（`recognize(image) -> {text, conf}`），默认实现 = RapidOCR；
2. **M0 阶段用用户真实笔记实测 RapidOCR**：拍 30 页不同书写习惯/科目 → 统计识别效果。若整体可用 → 默认 RapidOCR（免费+隐私）；若明显不可用 → 切百度手写 API（换一个实现类即可，接口不变，不动架构）；
3. 最终方案由 M0 实测数据说话，不拍脑袋。

### 6.3 校对闭环（产品可信度根基）
- 每页 OCR 文本可编辑（电脑端左右分栏批量校对 + 手机端单页可改）
- 保存修正 → 直接 UPDATE 记录 + 重建该页 FTS 索引 → 搜索立即用新文本
- 识别质量差的页（置信度低/文本过短）在列表标记「待校对」，引导用户处理

### 6.4 OCR 任务队列（MVP 简化版）
- 上传接口同步建页、立即把图片路径丢进**内存队列 + 后台 worker**（FastAPI BackgroundTasks 级别即可，单用户量级不需要 Celery/Redis）
- 状态机：`pending → processing → done / failed`，客户端轮询页状态（含失败原因+可手动重试）
- 服务器重启丢队列兜底：启动时扫描 `ocr_state=pending/processing` 的页自动重新投递（幂等）

## 七、数据模型（SQLite，7 张表以内）

```
users
  id PK, email UNIQUE, password_hash, created_at

subjects                       -- 学科（用户自管理）
  id PK, user_id FK, name, color, icon, sort_order, created_at

chapters                       -- 章/主题（学科下二级分组，可空）
  id PK, subject_id FK, name, sort_order, created_at

pages                          -- 核心：一页笔记 = 一张图 + 一段文字
  id PK, user_id FK
  subject_id FK, chapter_id FK NULL
  title                      -- 标题（默认取 OCR 首行，可改）
  image_key                  -- 原图存储 key（磁盘路径/OSS key）
  thumb_key                  -- 缩略图 key（列表用，服务端生成）
  ocr_text                   -- OCR 全文（可人工修正，修正即终稿）
  ocr_state                  -- pending | processing | done | failed
  ocr_error, ocr_conf        -- 失败原因 / 平均置信度
  page_no                    -- 章内页码（可选排序）
  width, height              -- 原图尺寸
  created_at, updated_at

-- FTS 索引（SQLite FTS5 trigram，中文子串搜索）
pages_fts (page_id UNINDEXED, title, ocr_text, tokenize='trigram')

-- 备注：trigram 要求连续 ≥3 字符匹配，2 字词可命中（作为 3-gram 子串）；
--       若实测不够，退回 LIKE '%kw%'（个人量级也毫秒级），二者选一，不叠加复杂度。
```

**不需要的表**：OCR 任务表（状态在 pages 上）、设备表（v2 再想）、分享表（不做）。

## 八、API 设计（草案，REST + JWT）

```
认证
  POST /auth/register          {email, password, nickname?}
  POST /auth/login             {email, password} -> {token}
  GET  /auth/me

学科
  GET    /subjects                      列表（含每学科页数统计）
  POST   /subjects                      {name, color, icon?}
  PATCH  /subjects/{id}                 改名/改色/排序
  DELETE /subjects/{id}                 页归入「未分类」或级联删除（前端确认弹窗）

章节（可选，MVP 可先只做学科一级）
  GET/POST/PATCH/DELETE /subjects/{id}/chapters

页
  POST   /pages               multipart: file + subject_id + chapter_id?    → 建页并投 OCR
  POST   /pages/batch         multipart: files[] + subject_id               → 批量（电脑端导入）
  GET    /pages?subject_id=&chapter_id=&state=&page=&size=   分页列表
  GET    /pages/{id}          详情（含 ocr_text / ocr_state）
  PATCH  /pages/{id}          改标题/移动学科/改 ocr_text（触发 FTS 重建）
  DELETE /pages/{id}
  POST   /pages/{id}/reocr    重新识别（失败重试/拍糊重拍）

搜索
  GET /search?q=导数&subject_id=数学&page=&size=
  → [{page_id, thumb, title, subject, snippet(命中上下文), ocr_state}]

图片
  GET /files/{key}            原图/缩略图（鉴权：登录态或短期签名 URL）

AI 学情（v2，轻量单次请求）
  POST /ai/study-report     body: {subject_id?} → 同步生成（约 5~15s）
                            → 服务端组装：学科统计 + 页标题文本 → DeepSeek → {report_md, stats}
                            限流：每用户每 5 分钟 1 次（成本控制）

备份（v2）
  GET /export                 整库 ZIP（图片 + 文本 JSON + 学科结构，可恢复）
```

## 九、手机端设计（Flutter）

### 9.1 页面清单（IA）
```
启动/加载 → 首页
首页（4 tab 底部导航，IA 原则）：
  ├─ Tab1 笔记库：学科卡片墙（进度=识别完成占比）→ 点进学科 → 章列表 → 页网格
  │        顶部搜索框（点击进 Tab3 或直接下拉搜索）

拍摄流程（全屏独立路由，非 tab）：
  拍照或相册多选(可连拍) → 逐张裁剪(4角拖动+旋转+增强滤镜滑块) → 选学科(可新建)

  大图（双指缩放，Hero 共享元素过渡）→ 下方信息卡：学科/章/标题(可改)/OCR 文本(可编辑)

AI 学情页（v2，入口=学科详情页顶部按钮 + 「我的」页入口，不占导航位）：
  上部统计卡（页数/识别完成率/近 30 天趋势，本地图表渲染）→ 「生成 AI 学情报告」按钮
  → 骨架屏加载（光效）→ 报告卡渐显（薄弱点提示 + 复习建议 + 参考页）→ 复制/导出
  （免费内测 → 稳定后按次收费，见《AI接入与按量计费》教学文档）
```

### 9.2 UI 风格方向（正式提案前先确认）
- **设计语言基础**：大圆角(20-32) + 宽松间距 + 玻璃质感卡片（**注**：配色与主题已在后续版本演进为深色主题，详见仓库当前实现） + MaShanZheng 仅用于品牌标题
- 学科卡片/封面可用「纸质笔记质感」差异点：学科色块 + 微弱纸张纹理 + 左上角折角，呼应「手写笔记」主题（待 UI 提案评审）
- 深色模式：v2 做，沿用深色光影规范（发光克制、线条 SVG 图标、禁 emoji）

### 9.3 动效清单（按用户「高级感=动效优先」标准，UI 提案必须逐项兑现）
| 元素 | 动效 | 曲线/时长 |
|---|---|---|
| 首页学科卡入场 | 交错上浮（逐卡错峰 60ms） | cubic-bezier(.22,1,.36,1)，0.5s |
| 学科卡按压 | 缩放回弹 | scale 0.96，150ms |
| 网格→详情大图 | Hero 共享元素过渡 | easeInOutCubic 350ms |
| 拍摄保存后归档 | 保存成功 → 卡片飞入笔记库对应学科（位置动画） | spring |
| OCR 状态 | 识别中 = 卡片角标脉冲光点；完成 = 勾号弹性出现 | 脉冲 1.2s 循环；勾号 spring |
| 搜索页 | 结果列表交错入场 + 关键词高亮渐显 | 错峰 50ms；高亮 250ms |
| tab 切换 | 微信式：点按瞬切，滑动跟手（惯用做法 jumpToPage） | —— |
| 底部/主按钮 | 按压回弹 + 悬浮微光 | 150ms / 呼吸 3s |
| 空态 | 空态插图 + 引导文字浮现（无数据真实空态，不用假数据——铁律） | 300ms easeOut |

### 9.4 交互铁律
- 拍照/导入**全真实**：image_picker 拍照/相册，无模拟网格
- 每页保存后真实出现在列表，OCR 状态真实轮询，失败可重试
- 分类（学科）用户自管理：长按 600ms 编辑/删除（微动 8px 不取消），「全部/未分类」固定
- 错误提示具体化（409/422 友好文案），前端预校验拦截
- 不做强制登录：游客可浏览本地缓存内容，操作触发登录弹窗

## 十二、里程碑与验收

### M0 —— 技术验证（先于一切开发，约 1~2 天）
- 云服务器装 RapidOCR，跑通单张识别

- 验证 SQLite FTS5 trigram 中文搜索（含 2 字词、识别错字场景）
- **产出**：OCR 选型决策记录（附实测数据）
- **验收**：决策有据可依，样本页留存作后续回归基准

### M1 —— MVP（约 2~3 周）
后端：认证/学科/页 CRUD/批量/搜索/FTS 同步/OCR 队列全套 + 测试
手机端：Tab 框架 + 学科管理 + 拍照裁剪归档 + 浏览 + 搜索 + OCR 状态
电脑端：同账号浏览搜索 + 批量导入 + **批量校对**（闭环关键）
- **验收**：端到端真机走通——真拍 10 页 → 归档 → OCR 完成 → 搜索命中 → 校对改错字 → 再搜即准；后端测试全绿；打包前对照功能清单回归

### M2 —— 体验补全 + AI 学情（约 2 周）
标题自动生成 / 识别失败重试引导 / 待校对队列页 / 导出备份 ZIP / 深色模式 / 动效清单逐项兑现（按 UI 提案确认稿）

- **验收**：真数据（≥1 学科 ≥10 页）报告内容合理且 <15s；数据过少时空态引导正确；接口限流生效

### M3 —— 打磨发布（按需）

## 十三、风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| 手写 OCR 识别率不达预期（最大风险） | 高 | M0 真实样本实测再选型；校对闭环兜底；印刷体场景保底价值；识别失败可重拍/重试 |
| 中文搜索体验（分词/错字） | 中 | FTS5 trigram 子串匹配 + LIKE 兜底；校对修正即改索引；v3 再加模糊/拼音容错 |
| 国内安卓无 GMS，自动裁剪难做 | 中 | MVP 手动 4 角裁剪（可靠）；不依赖 ML Kit |
| 笔记隐私顾虑 | 中 | 自部署 OCR 不出服务器；备份功能用户自持数据；HTTPS |
| 手机端存储与同步冲突 | 低 | MVP 服务端为准 + updated_at；v2 离线队列再细化冲突策略 |
| 服务器成本 | 低 | 与既有项目共用一台 2核4G；图片量大后转 OSS；单用户量级无压力 |
| 识别「完美主义」蔓延（用户/开发者想无限提升识别率而拖期） | 低 | 明确 80 分交付：识别 + 校对闭环 已构成可用产品，识别率提升作为长期项 |
| AI 报告质量不稳 / 成本失控 | 低 | 只发统计+标题（prompt 限长），单次 <1 分；接口限流（5 分钟 1 次）；输出带「仅供参考」 |
